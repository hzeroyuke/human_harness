# 日常使用、反馈与固定样本重放

这套流程把同一条回复的原稿、审阅过程、实际发出的文字和个人反馈关联起来。样本保存在本机；重放只重新运行审阅，不会重新执行开发任务或工具。

## 在自己的项目里启动

依赖已按主 README 安装后，在 Pi 的 `settings.json` 中增加：

```json
{
  "humanize": {
    "enabled": true,
    "record": true,
    "maxRevisions": 2,
    "timeoutMs": 120000,
    "maxContextChars": 48000
  },
  "extensions": [
    "/你的源码路径/human_harness/packages/coding-agent/examples/extensions/humanize-feedback.ts"
  ]
}
```

`record` 默认关闭，需要主动开启。扩展路径替换为本机绝对路径。模型与认证仍使用 Pi 的配置；也可以通过 `PI_CODING_AGENT_DIR` 使用独立的个人配置目录。

```bash
cd /你要开发的项目
/你的源码路径/human_harness/pi-humanize.sh --name "修复登录问题"
```

启动脚本保留当前工作目录。`PI_HUMANIZE=0` 可在下一次启动时关闭审阅；此前执行过的工具不会因此撤销。关闭审阅时也不会产生新的审阅轨迹。

## 当场给一条回复反馈

在 Pi 中输入：

```text
/feedback
/feedback 好
/feedback --choose
/feedback <traceId> 丢事实 --note "退款金额消失了" --expected "保留金额并说明下一步"
/feedback <traceId> 差 --tags 丢事实,太长 --note "我要的是下一步操作"
```

无参数时选择评分，再填写备注和期望表达。默认目标是当前分支最近一条记录；如果最新助手回复没有记录，命令会提示而不会默默评价上一条。`--choose` 可选择当前分支更早的回复，指定 ID 可以精确评价同一条。审核失败的记录也能评价。评分只保存为会话附加记录，不作为新消息发送给主模型，也不会额外调用模型。

反馈重点是你实际遇到的问题：哪个词没看懂、哪句话让你误解、哪个事实被改掉、是否太长。期望表达写一两句话就够了。看过原稿和改写稿后，再在备注里写“原稿更好 / 差不多 / 改写更好 / 两者都不好”。

原本清楚的回复也要留一些正常样本。不要只收集失败案例，否则很容易把系统改成“每次都啰嗦解释”。

## 导出自己的固定样本

在 Pi 中用 `/session` 查看会话文件位置。下面命令在源码仓库根目录执行；使用独立配置时，先设置相同的 `PI_CODING_AGENT_DIR`。

```bash
mkdir -p /你的本地评估目录
node --import ./packages/coding-agent/src/experimental/source-resolver.ts \
  scripts/humanize-personal.ts export /你的会话目录 \
  --output /你的本地评估目录/samples-v1.json
```

输入既可以是单个 `.jsonl` 会话文件，也可以是目录。默认导出全部记录；想先看问题样本并留正常对照：

```bash
node --import ./packages/coding-agent/src/experimental/source-resolver.ts \
  scripts/humanize-personal.ts export /你的会话目录 \
  --problems-only --keep-normal 5 \
  --output /你的本地评估目录/problems-v1.json
```

输出目录需先创建，输出文件必须不存在，源会话不会被改动。复制或分叉的会话会跳过继承自旧会话的轨迹并统计数量；导出包含原会话的目录，可以保留这些原始样本而不重复计算。保存好一份样本后，每次用同一个文件测试，避免样本集随日常会话变化。

## 在同一原稿上更换读者模型

```bash
node --import ./packages/coding-agent/src/experimental/source-resolver.ts \
  scripts/humanize-personal.ts replay /你的本地评估目录/samples-v1.json \
  --provider personal-copilot --model gpt-6-astra \
  --output /你的本地评估目录/astra-v1.json
```

`personal-copilot` 是本机示例配置的 provider，替换为你实际配置的名称。每个读者模型单独输出一份新文件；可重复 `--trace-id <id>` 只测试指定样本。模型请求会使用所选提供方，消耗它的用量。

重放使用当前源码的审阅逻辑，以及保存的原稿、可见对话与可用的执行快照。最初的读者仍只看用户可见对话，只有查证调用可以看到执行记录。它不会运行原会话中的工具，不会重新修改项目，不会把重放稿冒充当时发出的回复。

每条结果关联原始 `traceId`，保存新回复或明确失败、用量、耗时及源码指纹。一条失败不阻止其他样本运行。缺失必要背景时明确失败，不用空数据或猜测补齐。

## 打开本地对照报告

```bash
node scripts/humanize-personal-report.mjs \
  /你的本地评估目录/samples-v1.json \
  --replay /你的本地评估目录/astra-v1.json \
  --output /你的本地评估目录/report-v1.html
```

用浏览器打开生成的 HTML。它不依赖远程服务，内容来自本地导出文件；可以筛选样本、并排看原稿 / 当时实际发出的回复 / 新的重放结果，展开阶段与反馈。没有重放文件时省略 `--replay`，先检查日常原稿与最终稿。

HTML 包含样本全文，和 JSON 一样应留在本地。代码不会把这些文件自动上传 GitHub Pages。

## 一套轻量的个人评估节奏

**平时**固定一个主模型和一份配置。每个任务命名；看到问题就 `/feedback`，每天另抽查一条正常回复。先收集一周，比一开始反复换模型更容易定位问题。

**每周**固定 20–30 条样本，其中保留正常短回复、开发进度、最终交付、失败与限制、长对话追加需求和内部术语。一次只改读者模型或提示词中的一个主要因素。保留一部分任务不用于调提示，最后再验；同一任务的多条消息放在同一组，避免近似样本影响判断。

| 维度 | 看什么 |
|---|---|
| 好懂程度 | 更好、持平、退步各多少；是否减少追问 |
| 事实保留 | 数字、时间、路径、完成状态、限制有没有丢失或改错 |
| 工作打断 | 原文已经清楚却被拦住的次数；分别记录模型接口错误和审阅失败 |
| 等待与用量 | 额外等待、模型调用和 token 是否值得 |
| 任务交付 | 用实际业务检查判断是否完成，独立于表达评分 |

发布个人配置前，至少要求固定样本不新增事实错误、改善多于退步、误拦截与等待可以接受。自动批准率、改写次数和字数增加都不是质量分数。当前工具支持采集、重放和人工比较，不会把模型自评当作你的偏好，也不会自动把反馈写回系统提示词。

## 记录边界

- 原稿和实际保存的助手消息用消息 ID 关联；引擎批准稿与扩展事后改动的实际稿分别保留，不能混为一谈。
- `humanize_trace` 和 `humanize_feedback` 是附加记录，不进入主模型对话。只有开启 `record` 的新回复才有完整配对，旧会话不能补造原稿。
- 执行快照只保留可读助手文字、工具调用和工具结果，不保存思考块、系统提示和图片。工具文字仍可能包含项目敏感内容，这不等于自动脱敏。
- 大型快照可能超出记录限额，记录会说明不完整；缺少必要快照的重放不能当作完整背景下的比较。
- 纯工具响应无需表达审阅，不生成文字配对。主模型因输出限额截断的原稿会保留诊断，报告明确标为“主模型回复未完成，未进入读者审阅”；首次主模型接口调用就失败时没有可审阅原稿，不生成审核轨迹。
- 当前仍采用先审阅后显示；后台观察与审核失败自动放行原稿均未实现。
